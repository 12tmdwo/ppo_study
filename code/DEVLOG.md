## 1. 프로젝트 개요

### 목표
- **동작**: M0609 팔 끝에 단 밀대로 작업대 위 상자를 밀어, 무작위로 정해지는 목표 지점에 놓는다.
- **학습 방법**: 강화학습 PPO 알고리즘을 라이브러리 없이 **직접 구현**한다.
- **실행 환경**: 실제 로봇 없이 NVIDIA Isaac Sim + Isaac Lab 시뮬레이터에서만 학습·평가한다.

### 동기
- 강화학습을 라이브러리 사용법이 아니라 **원리 수준에서 이해**하는 것이 목적이다.
- 물체를 미는 동작은 마찰·미끄러짐 때문에 사람이 순서를 미리 짜기 어렵다. 결과를 보며 계속 고쳐야 하는 동작이라 강화학습이 잘 맞는다.

### 최종 결과물 (예정)
- 직접 구현한 PPO 코드 + 핵심 부분 검사 코드
- M0609 상자 밀기 학습 환경 코드
- 학습된 정책으로 상자를 미는 시뮬레이션 영상
- 학습 곡선, 성공률 기록 (이 문서의 7장)

## 2. 개발 환경

| 항목 | 내용 |
|---|---|
| OS | Ubuntu 24.04.5 LTS |
| CPU / GPU | Ryzen 5 7500F / RTX 3080 Ti (12GB) |
| NVIDIA 드라이버 | 580.178.04 |
| 파이썬 환경 | conda `env_isaaclab` (Python 3.12) |
| 시뮬레이터 | Isaac Sim 6.1.0 (pip 설치) |
| 학습 프레임워크 | Isaac Lab 3.0.0rc1 (pip 설치, 2026-10-09) |
| 비교 기준 PPO | rsl-rl-lib 5.4.1 (Isaac Lab 내장) |
| 딥러닝 | PyTorch 2.11.0 + cu128 |
| 로봇 모델 | 두산 공식 `doosan-robot2/dsr_description2`의 `m0609_isaac_sim.urdf`, `usd/m0609.usd` |

### 설치 방법 (재현용)

```bash
conda activate env_isaaclab
pip install uv
uv pip install "isaaclab[isaacsim,rsl-rl]==3.0.0rc1" \
  --overrides "https://raw.githubusercontent.com/isaac-sim/IsaacLab/v3.0.0-EA/tools/wheel_builder/uv-overrides.txt" \
  --extra-index-url https://pypi.nvidia.com \
  --index-strategy unsafe-best-match
```

- 공식 문서 명령어에는 `rsl-rl`이 빠져 있어서 추가했다.
- 버전 고정 목록(overrides)이 `torch==2.11.0`이라 기존 PyTorch(cu128)는 그대로 유지된다. 설치 전에 `--dry-run`으로 확인했다.
- 버전이 바뀐 패키지는 `newton`(1.5.0→1.5.2), `warp-lang`(1.17.0→1.16.0), `usd-exchange`(3.0.0→2.3.0) 3개뿐이다.
- 설치 전에 패키지 목록을 `~/env_isaaclab_backup_20261009/`에 백업했다 (`pip_freeze.txt`, `conda_explicit.txt`).

설치가 제대로 되었는지는 Isaac Lab에 들어 있는 Cartpole 예제를 내장 PPO로 학습시켜서 확인했다.

```bash
export OMNI_KIT_ACCEPT_EULA=yes
isaaclab train --rl_library rsl_rl --task Isaac-Cartpole-Direct physics=isaacsim_physx
```

## 4. 주요 결정 기록

> 면접에서 "왜 그렇게 했나요?"에 답할 수 있도록 **무엇을, 왜, 다른 선택지는 무엇이었는지** 남긴다.

### 결정 1. 첫 동작으로 "상자 밀기" 선택 (2026-10-09)
- **선택지**: 상자 밀기 / 집어서 들어올리기 / 쟁반 위 공 균형 잡기 / 공 던져서 맞히기
- **결정**: 상자 밀기
- **이유**
  - 잡는 순간의 접촉 물리(집게 설정)가 필요 없어서 첫 성공까지의 위험이 낮다.
  - 그래도 마찰·미끄러짐에 대응해야 해서 강화학습이 의미 있는 문제다.
  - 같은 팔 끝 도구 계열로 "집기 → 옮기기"까지 자연스럽게 확장할 수 있다.

### 결정 2. PPO를 라이브러리 없이 직접 구현 (2026-10-09)
- **선택지**: 검증된 라이브러리 사용 / 직접 구현 / 라이브러리로 먼저 성공 후 직접 구현으로 교체
- **결정**: 직접 구현. 단, 시뮬레이터 연결 같은 반복 작업은 미리 준비하고 PPO 핵심만 직접 작성한다.
- **이유**: 이 프로젝트의 목적이 결과물보다 **강화학습 원리 이해**이기 때문이다.

### 결정 3. 환경은 Isaac Lab 3.0, 알고리즘은 직접 구현 (2026-10-09)
- **선택지**
  - A. Isaac Lab으로 환경 구성 + 직접 구현한 PPO
  - B. Isaac Lab 없이 Isaac Sim만으로 병렬 환경까지 전부 직접 구현
- **결정**: A
- **이유**
  - B는 시간 대부분을 로봇 복제, 일괄 리셋 같은 시뮬레이터 관리 작업에 쓰게 되어 목적에서 벗어난다.
  - Isaac Lab은 GPU에서 수천 개 환경을 동시에 돌려 학습 시간이 짧다.
  - Isaac Lab에 검증된 PPO(`rsl_rl`)가 들어 있어 **비교 기준**으로 쓸 수 있다.
- **위험**: Isaac Lab 3.0은 정식 출시(2026년 10월 말 예정) 직전 시험판(`3.0.0rc1`)이다. 인터넷 예제 대부분이 2.x 기준이라 그대로 따라 하지 않는다.

### 결정 4. 로봇 전에 Cartpole로 PPO 먼저 검증 (2026-10-09)
- **이유**: 로봇 환경은 변수가 많아서 PPO 버그와 환경 버그를 구분하기 어렵다. Cartpole은 1분 안에 학습되고 로봇 환경과 연결 방식이 같아서, 여기서 검증한 PPO를 그대로 로봇에 쓸 수 있다.
- **원인 분리 규칙**: 학습이 안 되면 같은 환경을 `rsl_rl`로 돌려본다.
  - `rsl_rl`도 안 됨 → 환경 문제
  - `rsl_rl`은 되고 내 PPO만 안 됨 → PPO 문제

### 결정 5. "상자 밀기" 전에 "목표 위치로 가기" 단계 추가 (2026-10-09)
- **이유**: 상자 밀기는 "상자까지 가기 + 밀기"가 섞인 문제다. 로봇 설정이나 행동 크기 조절이 잘못됐을 때 원인을 찾기 쉽도록 상자 없는 문제로 먼저 확인한다. 나중에 여러 동작으로 확장할 때 그대로 하나의 동작이 된다.

### 결정 6. 여러 동작을 한 모델로 학습하는 건 나중에 (2026-10-09)
- **배경**: 모델 입력에 "지금 할 일 표시"를 함께 넣으면 한 모델이 여러 동작을 배울 수 있다(멀티태스크 강화학습).
- **결정**: 우선 동작 하나를 제대로 성공시키고, 나중에 확장할 수 있게만 설계한다.
- **이유**: 동작끼리 서로 학습을 방해할 수 있어 첫 프로젝트로는 위험이 크다. 확장할 때는 같은 팔 끝 도구로 할 수 있는 동작끼리 묶는다.

### 결정 7. 설계는 각 단계 직전에 필요한 만큼만 (2026-10-09)
- **선택지**: 처음에 전체 설계를 다 정하기 / 단계 직전에 그 단계 설계만 정하기
- **결정**: 단계 직전에 정하기
- **이유**
  - 코드를 더 빨리 시작할 수 있다.
  - 강화학습에서 가장 중요한 "점수 주는 법"(④)은 PPO를 직접 짜본 뒤에 정해야 왜 그렇게 줘야 하는지 제대로 이해할 수 있다.

### 결정 8. PPO 직접 구현 범위: 원리가 담긴 4가지 (2026-10-09)
- **선택지**: 적게(이득 계산·PPO 손실만) / 보통(+행동 뽑기·고치기 반복) / 많이(+신경망·저장소)
- **결정**: 보통. 행동 뽑기, 이득 계산(GAE), PPO 손실, 고치기 반복을 직접 짜고, 평범한 신경망·저장소·시뮬레이터 연결은 준비된 코드를 쓴다.
- **이유**: 강화학습 원리가 담긴 부분은 전부 직접 짜되, 원리와 관계없는 부수적인 작업에 시간을 쓰지 않기 위해서다.
- **검증 방식**: 빈칸마다 검사 코드로 확인하고, `rsl_rl`과 같은 설정으로 수레-막대 학습 결과를 비교한다. 결과가 운이 아니라는 것을 보이기 위해 씨앗값 3개에서 모두 통과해야 한다.
- 자세한 내용은 [1단계 설계 문서](docs/specs/2026-10-09-stage1-ppo-design.md)에 정리했다.
- 결정 9에서 "학습 속도 조절"이 추가되어, 직접 구현하는 부분은 5가지가 되었다.

### 결정 9. 학습 속도 자동 조절을 직접 구현하는 빈칸으로 추가 (2026-10-10)
- **배경**: 준비한 코드에 정답 구현을 넣어 미리 확인했더니, 씨앗값 3에서 통과 기준에 못 미쳤다. 원인은 학습 속도를 0.001로 고정한 설정이었다 (6장 [오류-1]).
- **선택지** (각각 씨앗값 3개로 실험한 뒤 비교했다. 7장 실험 3~5)
  - 가. 학습 속도를 0.003으로 고정: 통과하지만, 수레-막대에 맞춘 숫자라서 M0609에서는 다시 찾아야 한다.
  - 나. 반복이 끝날 때마다 KL을 보고 조절: 씨앗값 3에서 잘 되다가 무너졌다. 조절하는 간격이 길어서 반응이 늦다.
  - 다. 미니배치마다 KL을 보고 조절 (`rsl_rl`과 같은 방식): 통과했고, 학습 속도가 `rsl_rl`과 거의 같았다.
- **결정**: 다. 그리고 이 기능을 준비된 코드로 두지 않고, 사용자가 직접 채우는 빈칸(바-1)으로 추가한다.
- **이유**
  - 알아서 조절하므로 M0609 환경에서도 숫자를 다시 찾지 않고 그대로 쓸 수 있다.
  - `rsl_rl`과 같은 방식이라서, 나중에 학습이 안 될 때 `rsl_rl`과 비교해서 원인을 가리기 쉽다.
  - 코드가 6줄 정도로 짧고, KL이라는 지표가 왜 중요한지 직접 체험할 수 있다.

### 기록

### [오류-1] 정답 구현으로도 통과 기준에 못 미침 (씨앗값 3)
- **날짜 / 단계**: 2026-10-10 / 1단계 (빈칸 코드를 사용자에게 넘기기 전의 사전 확인)
- **증상**: 준비한 코드에 정답 구현을 넣고 씨앗값 1, 2, 3으로 학습시켰다. 씨앗값 1, 2는 통과했지만 씨앗값 3은 평균 총점 4.61, 평균 판 길이 282.0으로 기준(4.5, 290)에 못 미쳤다. 이때 검사 코드는 전부 통과하는 상태였다.
- **원인 찾은 과정**
  1. 학습 과정을 처음부터 살펴봤다. 학습 자체는 되고 있었지만 느렸다. 기준을 처음 넘은 반복이 84, 43, 138번째였고, `rsl_rl`은 26, 31, 44번째였다.
  2. 학습 상태 지표를 확인했다. KL이 0.002~0.004, 잘린 비율이 0.01~0.09로 정상 범위보다 작았다. 신경망이 한 번에 바뀌는 양이 작다는 뜻이다.
  3. `rsl_rl`의 tensorboard 기록에서 학습 속도(`Loss/learning_rate`)를 읽어 봤다. `rsl_rl`은 학습 속도를 최대 0.01까지 올렸고, 평균은 0.005~0.007이었다. 고정해 둔 0.001의 5~7배이다.
  4. "처음 설계에서 빼 둔 학습 속도 자동 조절이 원인"이라는 가설을 세우고, 해결 방법 세 가지를 임시 폴더에서 씨앗값 3개씩 실험했다 (7장 실험 3~5). `rsl_rl`과 같은 방식으로 조절했을 때 기준을 넘는 시점이 28, 33, 49번째로 `rsl_rl`과 거의 같아져서 가설이 맞음을 확인했다.
- **원인**: 코드의 잘못이 아니라 설정의 차이였다. `rsl_rl`은 KL을 보고 학습 속도를 자동으로 조절하는데, 처음 설계에서는 이 기능이 PPO의 핵심이 아니라는 이유로 빼고 0.001로 고정했다.
- **해결**
  - `ppo/ppo.py`에 빈칸 바-1(`adapt_learning_rate`)을 추가했다. 미니배치마다 KL이 목표(0.01)의 2배보다 크면 학습 속도를 1.5로 나누고, 절반보다 작으면 1.5를 곱한다 (범위 0.00001~0.01).
  - `ppo_update`(바-2)가 미니배치마다 이 함수를 부르도록 설명을 고쳤다. `PPOConfig`에 `desired_kl = 0.01`을 추가했다.
  - `ppo/train.py`가 실제 학습 속도를 기록하도록 고쳤다. 채점기 검사는 31개에서 38개로 늘렸다.
  - 고친 뒤 정답 구현으로 다시 확인한 결과, 씨앗값 3개가 모두 통과했다 (7장 실험 6).
- **배운 점**
  - 검사 코드를 통과하는 것과 학습 성능이 나오는 것은 별개이다. 정답 구현으로 전체를 미리 돌려보지 않았다면, 빈칸을 완벽하게 채우고도 원인을 모르는 미달을 겪었을 것이다.
  - "핵심이 아니다"라고 판단해서 뺀 기법이 학습 속도를 좌우할 수 있다. 비교 기준과 다르게 둔 설정이 있으면, 비교 기준의 기록을 열어서 실제 값을 확인해야 한다.
  - 조절하는 간격도 중요하다. 반복마다 한 번만 조절하면 반응이 늦어서, 잘 학습된 뒤에 한 번의 큰 수정으로 무너질 수 있다 (실험 4).
  - 검증된 비교 기준이 있으면 "느리다"는 막연한 증상을 숫자로 좁혀서 원인을 찾을 수 있다.

## 8. 용어와 지표 설명

> 처음 보는 용어와, 학습이 잘 되고 있는지 볼 때 쓰는 지표를 정리한다. 새 용어가 나올 때마다 추가한다.

### 용어

| 용어 | 뜻 |
|---|---|
| PPO | 강화학습의 학습 방법 중 하나이다. "해본다 → 점수를 받는다 → 점수를 잘 받은 행동을 더 하도록 신경망을 조금 수정한다"를 반복하되, 한 번에 수정하는 양을 제한해서 학습이 망가지지 않게 한다. |
| 환경 | 로봇(또는 수레-막대)이 움직이는 시뮬레이션 세계이다. 행동을 넣으면 다음 관찰값과 점수를 돌려준다. |
| 관찰값 | 환경이 신경망에 알려주는 현재 상태이다. 수레-막대는 수레 위치, 막대 각도, 수레 속도, 막대 각속도 4개이다. |
| 판(에피소드) | 시작부터 실패하거나 시간이 다 될 때까지의 한 번의 시도이다. 수레-막대는 최대 300걸음이다. |
| 정책 신경망 | 관찰값을 보고 어떤 행동을 할지 정하는 신경망이다. |
| 가치 신경망 | 관찰값을 보고 "앞으로 점수를 얼마나 받을지"를 예측하는 신경망이다. |
| 이득 | 그때 한 행동이 평소보다 얼마나 좋았는지를 나타내는 숫자이다. 실제로 받은 점수가 가치 신경망의 예측보다 높으면 양수가 된다. |
| GAE | 이득을 계산하는 방법의 이름이다. 여러 걸음에 걸친 오차를 섞어서 계산한다. |
| 미니배치 | 모은 경험 전체를 몇 개로 나눈 작은 묶음이다. 묶음 하나마다 신경망을 한 번 수정한다. |
| 학습 속도 | 신경망을 한 번 수정할 때 값을 얼마나 크게 바꿀지를 정하는 숫자이다. 크면 빨리 배우지만 학습이 무너지기 쉽고, 작으면 안정적이지만 느리다. |
| KL | 수정하기 전과 후의 정책이 얼마나 달라졌는지를 나타내는 숫자이다. 0이면 똑같고, 클수록 많이 달라진 것이다. 이 프로젝트에서는 KL이 목표(0.01) 근처에 머물도록 학습 속도를 자동으로 조절한다. |
| 씨앗값 | 컴퓨터가 무작위 숫자를 만들 때 쓰는 출발 번호이다. 씨앗값이 같으면 결과가 똑같이 재현된다. 결과가 운이 아니라는 것을 보이려고 씨앗값 3개로 실험한다. |
| rsl_rl | 스위스 취리히 공대 로봇 연구실이 만든, 검증된 PPO 프로그램이다. Isaac Lab에 함께 들어 있다. 이 프로젝트에서는 직접 구현한 PPO와 비교하는 기준으로만 쓴다. |
| 시간 초과 보정 | 판이 실패가 아니라 시간이 다 되어 끝났을 때, 미래 점수를 0으로 보지 않도록 점수에 가치 예측을 더해 주는 처리이다. |

### 학습 상태 지표

학습을 실행하면 반복마다 아래 값이 화면과 tensorboard에 기록된다.

| 지표 | 뜻 | 정상일 때 | 이상 신호 |
|---|---|---|---|
| 평균 총점 | 최근 끝난 100판에서 받은 총점의 평균 | 오르다가 평평해진다 | 오르지 않거나, 오르다가 무너진다 |

| 가치 손실 | 가치 신경망의 예측이 실제와 얼마나 다른지 | 처음에 크다가 줄어든다 | 계속 커진다 |
